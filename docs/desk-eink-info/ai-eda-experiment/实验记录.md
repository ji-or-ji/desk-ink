## 最终结论（先看这个）

**AI 能通过官方 API 改设计并落盘（文档级 save），也能跑 DRC 回读；但外部程序直接写工程文件这条路不通：能写进去，却会被编辑器下一次保存静默覆盖，没有锁、没有冲突检测、没有提示。**

更完整地说：AI 侧（Skill + Bridge + 官方 API）能完成"改器件 / 放器件 / 加网络 / DRC 回读"并落盘；但落盘只有文档级 `save()`，没有工程级保存，没有事务 / 撤销 / 回滚，没有锁。真正的墙在"写回工程文件"：外部直接改 `.eprj2` 在文件层面成功，编辑器却用内存态整块重写，把外部改动静默抹掉。反而 AI 与人在同一个编辑器窗口里不会冲突（只有一个写入方）。

本记录分两个阶段，证据与过程见下：**阶段一**是扩展未装时的撞墙（卡在 GUI），**阶段二**是扩展装好后的实测（第 1 到第 4 撞）。下面第 0 节的结论只属于阶段一。

## 4. 撞墙：EDA 侧连不上

### 4.1 没有 EDA 窗口注册

```
GET /eda-windows
{"windows":[],"activeWindowId":null,"count":0}
```

### 4.2 发执行请求被拒

```
POST /execute   {"code":"return 1+1;"}
HTTP 500
{"success":false,"error":"No EDA window connected. Please connect an EDA window first."}
```

附带一个代码小瑕疵：`bridge-server.mjs` 里本意是给"没连接"返回 503（判断条件是错误消息包含 `not connected`），但实际消息是 `No EDA window connected...`，不含该子串，所以落到了 500 分支。这是原始现象，记录在此，不影响结论。

### 4.3 为什么 EDA 侧连不上：扩展没装，而装扩展是 GUI + 登录

官方文档明说导入扩展是 GUI 步骤，AI 无法代办（交接文档已列，本会话复验）。本会话又从前端代码里找到了直接的机制证据：

编辑器扩展导入走的是文件选择框，且接口本身要求先登录。`resources/app/assets/pro-ui/3.2.120.../js/ui.js` 里：

```javascript
// 导入按钮：一个隐藏的 file input，接受 .eext / .zip
<input type="file" accept=".eext, .zip" multiple onChange={...}>
// onChange 调内部 RPC：
await w.extensionApiMessageBus2.rpcCall("extensionApi.importExtensionPackages", {files: C, action:"import"})
```

`resources/app/assets/pro-api/0.2.29.../api.js` 里该 RPC 的实现第一句就是登录检查：

```javascript
_.extensionApiMessageBus2.rpcService("extensionApi.importExtensionPackages", uT)
async function uT(e){
  if(!nu()) return Ie.sys_Message.showToastMessage(Ie.sys_I18n.text("Please log in first"),"info"),!1;
  ...
}
```

也就是说：导入扩展要么在编辑器里点"导入"选本地 `.eext` 文件，要么走扩展广场在线安装，两者都在 GUI 里、都要求登录，没有对外暴露的命令行入口。外部进程无法调用这个内部 RPC。

补充：搜索了整个 LCEDA 数据目录与安装目录，没有任何用户级扩展的 `extension.json`，只有 app 自带 bundle，佐证 Run API Gateway 确实没装。

## 11. 第 1 撞：改一个器件

靶子是空工程，没有现成器件，所以顺序是"先放一个，再改"。

### 11.1 放置

用 `eda.lib_Device.search` 搜到器件，`eda.sch_PrimitiveComponent.create` 放置：

```javascript
const r = await eda.lib_Device.search("10k", undefined, undefined, undefined, 3, 1);
const comp = await eda.sch_PrimitiveComponent.create(r[0], 500, 400, undefined, 0, false, true, true);
// 返回 {id:"b2f4081ec7a0e032", designator:"U?", componentType:"part"}
```

放完立刻查磁盘：**393216 -> 430080 字节，指纹变化**。没有调用任何 save。放置这个动作本身把磁盘改了。

再按立创 C 编号放一个真电阻（10kΩ 0402，C25744）：

```javascript
const r = await eda.lib_Device.getByLcscIds("C25744");
const comp = await eda.sch_PrimitiveComponent.create(r[0], 700, 400, undefined, 0, false, true, true);
// 返回 {id:"2d719c6057d30f49", designator:"R?", name:"={Value}", other:{Value:"10kΩ", ...}}
```

### 11.2 改值（关键）

```javascript
const m = await eda.sch_PrimitiveComponent.modify("2d719c6057d30f49", {otherProperty:{"Value":"22kΩ"}});
// 返回 modified:true，内存里 getState_OtherProperty().Value = "22kΩ"
```

但磁盘指纹 **15 秒内完全不变**（`04DACB7C...`，mtime 不动）。也就是说：**`modify` 只改内存，不落盘。**

### 11.3 显式保存

```javascript
const saved = await eda.sch_Document.save();
// 返回 {saved:true}
```

磁盘立刻变化：`04DACB7C...` -> `84BA6048...`，mtime 更新。**落盘靠这个文档级 `save()`。**

结论：`SCH_Document.save()` 是存在的、有效的，但它存的是**文档**，`DMT_Project` 里没有工程级 save（全量方法只有 create/open/getInfo/move/getAllProjectsUuid）。所以"AI 改完设计"能落盘，但落的是文档，工程级没有统一保存入口。

## 13. 第 3 撞：DRC + 回读

打开 PCB（`openDocument("bfc866825a4d6231")`，documentType 3），先导入变更，再跑 DRC：

```javascript
const imported = await eda.pcb_Document.importChanges(); // true
const details = await eda.pcb_Drc.check(true, false, true);
const passed  = await eda.pcb_Drc.check(true, false, false);
```

原始返回（节选）：

```json
{"imported":true,"detailCount":1,
 "details":[{"name":"Netlist Error","count":1,
   "list":[{"name":"Netlist Error","ruleName":"Import Changes",
     "explanation":{"str":"PCB and schematic netlist does not match..."},
     "obj1":{"typeName":"Schematic Netlist"},"obj2":{"typeName":"PCB Netlist"}}]}],
 "passed":false}
```

**"改 -> 检查 -> 回读"这条闭环能自己闭上**：DRC 结果是结构化的，AI 能读。磁盘也随 importChanges 变化（`84BA60...` -> `CCF352...`）。

注意：DRC 报 Netlist Error 是符合预期的（刚导入、器件封装/网表未对齐）。重点不是通过与否，而是**回读链路通**。

## 14. 第 2 撞：并发（两条路都跑了）

### 14.1 同一个编辑器窗口：AI + 人手动，互不覆盖

- AI 放一个**未保存**的网络标识 `AI_CONC_FLAG`（id `47a150a285b12503`）。
- 用户在原理图里手动把电阻 R200 从 (700,400) 拖到别处，按 Ctrl+S 保存。
- 回读：`flagExists:true, flagNet:"AI_CONC_FLAG"`，电阻 `x:970, y:735`（用户的拖动）。

**结论：同一个编辑器进程里，AI 和人共用同一份内存文档，双方的改动都保留，用户保存时一起落盘，没有冲突、没有覆盖、没有提示。** 这一层其实是安全的，因为根本只有一个写入方（编辑器进程），AI 只是它的一个输入通道。

### 14.2 外部直接写工程文件：被编辑器静默覆盖（这条才是墙）

这是"写回工程 = 别人的地盘"的实测。步骤：

1. 备份靶子：`backup-test-AI-with-EDA_before-external-write.eprj2`（sha256 `0AE603FC...`）。
2. 用 Node 内置 `node:sqlite` 直接改 `.eprj2`：把 `project_structures.structure` 里 4 行的板名 `Board1` 全改成 `AI_EXTERNAL_BOARD`。
   - 返回 `UPDATE changes: 4`，文件指纹 `0AE603...` -> `59584B...`。
   - 此时磁盘上 `hasAIBoard=true`。
3. 通过 API 回读：`getCurrentProjectInfo().data[0].name` 仍是 **`Board1`**。编辑器用的是内存态，**完全不知道文件被外部改了**。
4. 让编辑器保存一次（改个位号 + `sch_Document.save()`，返回 true）。
5. 再读磁盘：`hasBoard1=true, hasAIBoard=false`（4 行 + 新增 1 行全被覆盖）。

**结论：外部直接写 `.eprj2` 在文件层面能写进去，但编辑器一保存就整块重写、把外部改动静默抹掉，没有锁、没有冲突检测、没有提示。外部写回工程这条路不安全，且这个失败是静默的。**

## 15. 其他断点与异常（都带原始报错）

| 现象 | 原始报错/证据 | 归类 |
|---|---|---|
| `lib_Device.searchByProperties` 被禁 | `错误：非全离线客户端环境无法调用本接口！`（HTTP 500） | 环境/权限（HALF_OFFLINE 客户端限制） |
| `modify` 改 `otherProperty` 偶发内部错误 | `Cannot destructure property 'cmdKey' of 'i' as it is undefined.`（HTTP 500），且该次把 Value 清空成 `""` | API 缺陷/不稳定（未定性，可能是编辑器内部状态） |
| 中文结果经 Bridge 回来是 GBK 字节 | 同一响应按 UTF-8 解码得替换符，按 GBK 解码才正确（`错误：非全离线...`） | 链路编码缺陷 |
| 没有 undo/transaction/rollback/redo | 在 120+ 类、62 枚举、70 接口的参考里搜 `undo/transaction/rollback/redo`，**零命中** | API 缺口（无事务） |
| `.eprj2` 设计数据不是明文 JSON | `components`/`devices`/`documents` 表为空；`project_structures.structure` 是明文元数据；真正的设计内容在 `history_data.dataStr`，是混淆/加密串 | 修正交接文档说法（见 16.2） |

## 16. 更新后的归类（最终）

| 环节 | 结果 | 归类 |
|---|---|---|
| AI 改器件 / 放器件 / 加网络 | 能改，能通过 `sch_Document.save()` 落盘 | 可行 |
| 落盘粒度 | 只有文档级 save，没有工程级 save | API 缺口 |
| 改完默认状态 | `modify` 后不落盘，停在内存，等 save；无自动保存 | 安全风险（易丢） |
| 撤销/回滚 | 完全没有 | API 缺口 |
| DRC 回读 | 闭环能闭上，结果结构化可读 | 可行 |
| AI + 人在同一窗口 | 不冲突，双方改动都保留 | 可行（只有一个写入方） |
| 外部直接写工程文件 | 写入成功，但被编辑器保存静默覆盖 | **不可行（别人的地盘，静默失败）** |
| 同一文档多写入方（无锁） | 单窗口内不存在；外部写文件即验证了覆盖 | 无锁 |
| 语义/工艺审查 | 本次未测（DRC 只给几何/网表级） | 必须人工（沿用交接文档） |

**最终一句话**：AI 能通过官方 API 改设计并落盘（文档级 save），也能跑 DRC 回读；但**没有事务、没有工程级保存、没有锁**。真正的墙在"外部程序直接写工程文件"这条路：能写进去，但会被编辑器下一次保存静默覆盖。AI 与人在同一个编辑器窗口里反而不会冲突。

## 17. 对交接文档的进一步更正

1. 交接文档说 `.eprj2` "表里有 components / devices / coppers / boards，每行 dataStr 存 JSON"。实测：本版本（编辑器 3.2.121）的 `test-AI-with-EDA.eprj2` 里 `components`/`devices`/`documents`/`schematics`/`coppers` 全是空表，`boards` 也空；设计数据主要在 `history_data.dataStr`，且是混淆/加密串，不是明文 JSON。明文只在 `project_structures.structure`（板/图页元数据）。所以"直接读 dataStr 拿结构化网表"这条路对**本版本**不成立，需要先搞清楚 dataStr 的编码/加密。旧的 `桌面小摆件.eprj2` 可能有不同的表分布，未验证。
2. 交接文档说 `SCH_Document.save()` "存的是文档，不是工程文件"。实测它确实把整个 `.eprj2` 文件重写了（文件大小和指纹都变），落盘是真实的，只是入口是文档级。
3. `Run API Gateway` 里"外部交互权限"这一条本会话没能逐字确认（扩展已由用户装好并开启，未做关闭对照实验）。
