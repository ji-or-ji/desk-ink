# 设计变更请求 — 设备端上报配置

> 日期：2026-09-18
> **面向：硬件 / 固件会话**（opencode）　**只改 `software/`，不碰 `pc-tool/`**
> 配套：PC 端的接收与展示见 `变更-PC配置显示与预览.md`（另一个会话，本文件不依赖它）
> 前提：**设备是配置的主角，PC 是辅助**。设备大部分时间脱离电脑运行。

---

## 一、本次做什么

设备在**两个时机**把自己的六项配置用一条 `cfg` 消息报给 PC。

**就这些。** 不做接收、不做写回——那是第二步的事。

---

## 二、消息 `cfg`（设备 → PC）

全量，每次都发完整的六项：

```json
{"t":"cfg","refresh":1,"pomo_focus":25,"pomo_break":5,
 "rotate":1,"art_mode":0,"bar_mode":0}
```

约 88 字节，一帧装得下（上限 255）。

| 字段 | 取值 | 默认 | 对应 NVS key |
|---|---|---|---|
| `refresh` | 0 自动 / 1 常规 / 2 静默 | 1 | `cfg_refresh` |
| `pomo_focus` | 15 / 25 / 45 | 25 | `cfg_pomo_focus` |
| `pomo_break` | 5 / 10 | 5 | `cfg_pomo_break` |
| `rotate` | 0 关 / 1 开 | 1 | `cfg_rotate` |
| `art_mode` | 0 全屏 / 1 小窗 | 0 | `cfg_art_mode` |
| `bar_mode` | 0 实心 / 1 反色 / 2 反色自适应 | 0 | `cfg_bar_mode` |

字段名 = NVS key 去掉 `cfg_` 前缀。**以后加配置项往后加字段，不改已有字段名**（PC 端按名字取值）。

---

## 三、要改的地方

### 1. `components/link/include/link.h`

```c
typedef struct {
    int refresh;
    int pomo_focus;
    int pomo_break;
    int rotate;
    int art_mode;
    int bar_mode;
} link_cfg_t;

esp_err_t link_send_cfg(const link_cfg_t *cfg);
```

### 2. `components/link/link.c`

实现 `link_send_cfg()`，**照 `link_send_schedule()` 的写法**（`snprintf` 拼 JSON + 发送）。

### 3. `components/app/app.c`

加一个 `push_cfg()`，把当前 `s_cfg` 填进 `link_cfg_t` 后调用 `link_send_cfg()`。

**只在两个时机调用：**

| 时机 | 位置 |
|---|---|
| `hello` 发出之后 | 紧跟着发一次，让 PC 一连上就知道设备现状 |
| 本地配置页**保存**之后 | 让 PC 的显示跟着变 |

> 别加第三个时机（比如定时上报）。配置不是高频数据，多推是浪费电。

---

## 四、不改的地方

- `components/ui/**` —— 配置页 UI 已就绪，六项都在
- `components/store/**` —— NVS 读写够用
- **`pc-tool/**` 一个字都不改** —— 另一端单独一份变更
- 设备端不接收任何配置消息；收到未知类型按现有规则丢弃

---

## 五、验收

1. 上电后串口能看到一条 `cfg`，六个字段与设备实际设置一致
2. 在设备配置页把「信息条」改成「反色自适应」→ 串口又出一条 `cfg`，`bar_mode` 变成 2
3. 新建的 `cfg` 行不超过 255 字节
4. 断连、重连各试一次，行为不变（设备不因 PC 在不在而改变自己的配置）
