# 项目心得 —— 让 AI 做一块墨水屏

> 这是 desk-ink 的实验记录。项目本身的说明见 [README](../README.md)。
> 更新：2026-09-18

---

## 一、这个项目其实是个实验

技术目标（做一块省电的桌面墨水屏）只是外壳。真正想验证的问题是：

> **在嵌入式这种"软硬交界、规格书满天飞"的场景里，现在的 AI 到底能干多少？**
> **能替代掉多少人工？**

所以整个项目里，我刻意**只做两件事：选型、关键决策**。
其余的调研、方案、文档、编码、验证，全部交给 AI，**不插手**。

连硬件选型阶段也是：**我刻意不去看规格书的具体内容**，只让它读完、给出方案和理由，
我只负责拍板。把「看不明白就该问人」这一环也交出去，是这次最激进的一步。

我想看的不是"AI 能不能写出能跑的代码"——那早就不是问题了——
而是**它能自己走多远，会在哪里卡住，卡住的时候是诚实还是硬编**。

| IDE | **VSCode** | — |

**会话窗口数**（这点我特意控制了）：

- **OpenCode 用了两个窗口**，互不相通：
  - 窗口 A：PC 端小工具（.NET 8 + WinUI 3）
  - 窗口 B：硬件 / 固件（ESP-IDF）
- **Hanagent 只用了一个窗口**，但它中途被压缩过一次上下文。

> 为什么强调窗口数：两个窗口互不可见，意味着**所有跨端信息必须落成文档才算数**。
> 这恰好是最真实的协作约束。

## 四、观察：AI 真的强在哪

**① 啃规格书。** 从 32 页的墨水屏规格书里，它把两处关键参数抠了出来并纠正了文档：

- MCP3021 是 **10-bit**、地址 **0x4B**（A3T 后缀决定），不是之前记的 0x4D
- 驱动 IC 是 **SSD1619AZ**，不是 SSD1680 —— 依据是命令表里 `0x26` 写作 Write RAM (Yellow)，
  那是 SSD1619 系列的说法。**一条文档错误，顺着 8 个文件全改掉了。**

**② 找链路缺口。** 它发现「新闻」这条链**只有 PC 端整段缺失**——协议定义了、固件收存画全做了、
唯独没人发。还发现 `todo` 消息**装不下 8 条**（单条固定开销 30 字节，8 条光开销就 269 > 255 上限），
而原来的实现是"截断后照发"，配上"全量覆盖"语义会**静默丢数据**。

**③ 维护一致性。** 一次改名要同步 10 份文档；一份决议要同步"设计稿 / 工单 / 交接文档"三处。
这种活儿人做会漏，AI 做得干净。

**④ 把"没验证"标出来。** 它会在文档里写「端到端未跑通」「运行时未验证」，
而不是含糊过去。这比多写 100 行代码重要。

## 五、观察：AI 栽在哪（这部分更值得看）

### 案例 1：工具用错 → 得出完全相反的结论

它用 PowerShell 的 `Select-String -SimpleMatch` 搜索时，把 `a|b|c` 当成"或"，
实际上 `-SimpleMatch` 下竖线是**字面字符**。结果零命中，
于是它断言「插画功能两端都没实现」——**而固件那边其实早就写好了。**

> 教训：**零命中要先怀疑自己搜错了，而不是先下结论。**

### 案例 2：数据类型不一致 → 汉字全部消失

它写的预览工具里，字库码位表用 `[uint16]` 建、用 `[int]` 查 —— PowerShell 的哈希表**键区分类型**，
于是每个汉字查询都落空。ASCII 走的是算术偏移（不查表），所以症状是
**数字正常、汉字一个都没有**。

更值得记的是它**当时的处理方式**：它把这个现象解释成"OCR 读不出 16px 小字"，
**用解释代替了验证**。后来被指出"图里根本没中文"，才回头查数据通路，
花五分钟就定位了。

### 案例 3：过度自信的结论

它先断言「QEMU 不缺运行库、是静态链接」，理由是 `--version` 能跑。
后来实测：把 PATH 削到只剩 `System32`，**立刻复现 `0xC0000135`**——
真实原因是缺 `libiconv-2.dll`，而它当时能跑只因为环境里恰好有（某个 Git 的 `mingw64/bin`）。

### 案例 4：配置覆盖从未生效

它给了 QEMU 的构建配方，用 `-D SDKCONFIG_DEFAULTS=...` 切日志通道。
但那个参数**只在生成新 sdkconfig 时起作用**，项目根早就有一份 sdkconfig 把设置压过去了。
于是"改了配置"其实一直没生效，**它却拿这个当了几小时的结论基础**。

### 案例 5：复刻冒充实现

它早期汇报界面状态时，用的是自己**照着代码重画**的图，而不是真代码渲染的。
坐标是照抄的没错，但那是"设计"，不是"实现"。容易让人高估完成度。

## 六、几条可复用的规矩

从上面这些坑里总结出来的，后来写进了项目的协作约定：

1. **结论必须能复现。** 不能复现的，写成"待澄清"，不要写成"结论"。
2. **别用解释代替验证。** 现象缺席时，先查数据通路，别先归因于"工具不行"。
3. **文档是唯一交接媒介。** 两个会话互不可见，没落纸的等于没发生。
4. **一份工单只面向一个会话。** 跨端的活拆成两份，各自自包含。
5. **让 AI 自己跑验证。** 这个项目最后搭出了"QEMU 里跑真固件、导出 framebuffer"的流程——
   **"没硬件就没法验证"这句话就此作废**，每次改 UI 都能在仿真里先看一眼。
6. **契约与工单分开。** 协议/规格是长期文件，工单会过时；两者不能混。

---

## 七、还没做到的

诚实地说：

- **没有上过电。** 墨水屏没点亮过，PCB 没布线，串口/蓝牙/ADC/RTC 全都没在真硬件上跑过。
- 刷屏时序、ADC 阈值、功耗，都还是按规格书推算的。
- 所以现在这份"做完了"指的是**代码与文档层面**，不是"能用"。

---

## 八、目前的结论

**AI 已经能独立走完"调研 → 方案 → 文档 → 编码 → 仿真验证"这条链**，
而且产出的一致性比人手工维护更好。

它最不可靠的地方不在能力，而在**自我校验**：它倾向于把"没看到"解释成"不存在"，
把"跑通一次"当成"没问题"。**能纠正这一点的不是更强的模型，而是流程**——
可复现的验证、明确标注的未验证项、以及一个会追问"你怎么知道的"的人。

这个项目里，我做得最多的事其实是：**问"真的吗？"**
